# 快照恢复内存调查与优化建议（2026-09-23）

调查阶段只进行了生产只读检查和本机隔离实验。下文保留原始证据与方案，后续实现及验证见文末「实施记录」。

## 结论

恢复阶段降到约 50MiB 有实测支撑，但需要改变恢复方式，不能只把 DuckDB 的 memory_limit 改成 50MiB。整个 uni-api-analytics 服务（查询、历史追赶、账单、检测并发）的峰值限制到 50MiB，当前架构不满足，本次也没有证明能够满足。

推荐将分析历史单独存为可直接打开的 DuckDB 物理快照，恢复端仅流式下载、校验、解压、原子切换文件，再打开数据库；保留 Parquet 格式作为版本迁移及应急重建格式。同步改掉每个来源扫描前加载全量对象索引的行为。

## 测量口径与样本

- 使用从生产对象存储只读下载的一份快照，本机 macOS 隔离运行，每项实验是新的进程。
- DuckDB Go 驱动与仓库相同：v2.10505.0。
- 峰值是 getrusage 的进程 MaxRSS，包含 Go/CGo/DuckDB，单位 MiB；不等于 DuckDB buffer budget，也不等于 Linux cgroup memory.peak。
- 快照压缩文件 154,975,239 字节，约 147.8MiB。
- facts 3,536,242 行；rollups 869,223 行；imported_objects 375,920 行。
- 下载、解压与数据库实验分别使用独立进程；物理快照实验把解压、写盘、文件同步、打开及校验放在同一进程。物理快照的时间从本地压缩文件读取开始，不包含网络时间。
- 物理快照的生成没有验证为 50MiB；本次先用足够预算生成完整数据库，再测恢复端。不能把生成端成本搬走后声称整个系统峰值已经降到 50MiB。

| 路径 | 结果 | 进程峰值 RSS | 时间 |
| --- | --- | ---: | ---: |
| 原始 tar.gz 快照下载并解压 | 成功 | 21.86MiB | 25.00s（含本机网络） |
| 现有模式：索引已建，三表一次事务全量导入，预算 1GiB | 成功 | 1,017.80MiB | 15.24s（本地导入提交） |
| 50MiB 预算，单线程，preserve_insertion_order=false，仍保留现有索引 | facts 导入失败：49.8/50MiB 耗尽 | 89.52MiB | 0.50s 到失败 |
| 同样 50MiB 设置，按表单独提交 | 第一张 facts 表即失败 | 90.25MiB | 0.30s 到失败 |
| 直接打开已完成的 DuckDB 文件并核对三张表行数 | 成功 | 36.92MiB | 0.03s |
| 物理快照：流式解压、写盘、fsync、rename、打开并核对三表 | 成功 | 41.52MiB | 5.28s |
| 上述恢复后再做最近一小时的基础分组聚合 | 成功，返回 48 组 | 48.78MiB | 累计 5.37s |
| 现有 ImportedObjects() 加载一份全部对象索引 | 成功 | 233.58MiB | 累计 0.30s |
| 同时保留两份索引（对应两个来源的当前逻辑） | 成功 | 340.66MiB | 累计 0.49s |

物理数据库文件为 683,421,696 字节（约 651.8MiB），gzip 后约 217MiB，比现有 Parquet 压缩快照约多 47%。恢复后通过 cmp 验证文件逐字节相同。基础聚合不是完整控制台压测，也未验证所有增量写入、索引加载和查询均可在 50MiB 下运行。

另尝试无索引全表导入时受到本机临时磁盘空间限制，未形成有效内存比较，不用于上述结论。临时生产快照、凭据及实验数据已在调查结束后清理。

生产只读观测：进程 VmHWM 约 2,218MiB，当前 VmRSS 约 1,194MiB；容器 memory.peak 约 3,016MiB。这些是实例全生命周期/并发后台工作数据，不能归因成纯快照恢复峰值。容器统计还包含文件页缓存等开销。

## 已确认的开销来源

1. `analytics-api/checkpoint.go` 的恢复逻辑在一笔事务内将 facts、rollups、imported_objects 从 Parquet 全量写入，最后一起提交。
2. `analytics-api/engine.go` 先建立 facts.event_id、imported_objects.object_key 的主键，以及 facts_at 索引，再导入数据。恢复时会重新维护索引。事务、写缓冲及索引成本叠加；本次没有单独定量拆分这三者占比。
3. `ImportedObjects()` 无 source 条件读取完整表，构建 map[string]string；`importSingleS3()` 为每个来源调用一次。来源数和历史对象数增大会重复占用内存。
4. `startup.go` 同时启动账单、检测、绑定、自动化及历史恢复；`s3_import.go` 还有最多 16 个下载和按 256 个对象/16MiB 分组解析。原始字节大小不等于解码后的 Go 结构大小。
5. DuckDB memory_limit 不是整个进程的硬上限，降低它并不保证 MaxRSS 或 cgroup 峰值等比例下降。

## 推荐实现

### 第一阶段：物理快照 + 独立配置

- 把 facts、rollups、imported_objects 放到独立 facts.duckdb。价格、price_history、配置 meta 继续以现有 S3/控制数据库为权威来源，不随历史快照回退。
- 生成快照时对分析库建立一致性写入屏障，完成 CHECKPOINT；在没有并发写者时取得不可变副本。支持文件系统快照/reflink 时缩短屏障；否则在屏障内复制到暂存文件，再释放屏障、异步压缩上传。不能在写入进行中直接复制 .duckdb 并忽略 WAL。
- 快照 manifest 记录格式版本、DuckDB 存储版本、schema 版本、来源标识、文件长度/哈希、各表行数和覆盖范围。版本不兼容时才走 Parquet 迁移。
- 恢复到独立临时路径，以固定缓冲流式下载/解压并校验完整哈希。完成 fsync、轻量结构与行数校验后才原子切换；失败删除暂存文件，保留旧可用快照。
- 索引随物理文件保存并按需加载，避免每次启动全量重建。
- 恢复完成后先同步最新价格再放行统计；单独恢复工作进程/初始化容器，避免把所有业务后台任务一起计入恢复预算。控制与账号配置恢复应继续独立运行，不重新与历史预热绑定。

这一步恢复端目标可定为峰值 RSS 50MiB 左右；严格 50MiB cgroup 硬上限必须在 Linux 容器重新验证，当前 macOS 原型不能代替验收。文件页缓存应单独监测，必要时分段使用平台提供的缓存回收提示。

### 第二阶段：历史追赶取消全量 Go map

- 每次 S3 List 获取最多 1000 个对象后，用参数化批量查询/VALUES JOIN 同时检查这一页的 object_key、etag；只保存本页状态。
- 按 source 归属进行查找，不再为 Fugue、DigitalOcean 各复制一次完整 imported_objects。
- 保留对象键+etag 的幂等校验和“不可变对象被修改”的拒绝逻辑。不能简单使用最大时间戳跳过列表，否则会漏掉晚到数据。
- 以解码后的字节预算限制下载/解析队列，从 1–2 个并发、较小批次开始测；逐批释放对象数组。后台账单同步、检测、查询分别预算与限流。
- ART 主键在持续增量写入时仍可能加载大量索引，因此这一阶段不保证分析服务全生命周期 50MiB。如将它设为硬目标，需进一步评估磁盘去重索引与分区只读历史/小型增量库，属于更大的存储架构调整。

### 保留 Parquet 的低内存备选

- 将单个大文件改为小 row group/分片；在全新 staging 数据库中逐块导入并提交，校验完成后原子切换整个库。
- 单线程、关闭 preserve_insertion_order、限制临时磁盘占用。
- 评估删除无收益的 facts_at 索引、把必要索引的构建放到独立阶段。
- 不能在当前正在服务的库里逐表提交，否则失败时可能出现“事实已更新、汇总/去重索引未更新”的不一致。不能随意去掉唯一约束造成重复计费。
- 本次证据表明只改提交粒度/线程并不足以达到 50MiB；这不是优先方案。

## 验收要求

- Linux 相同镜像与真实快照，分别记录下载、解压、打开、校验、追赶、首次查询的进程 RSS、Go heap、DuckDB buffer、cgroup anon/file/peak、临时磁盘和耗时。
- 按当前、2倍、4倍历史规模测试。恢复端峰值不应随总历史量近似线性增加。
- 验证哈希、行数、按来源/Key/模型/时间的消费与成功率、重复回放不增加消费、最新价格不回退。
- 注入截断下载、校验失败、磁盘满、恢复中断、版本不兼容、晚到对象、并发价格修改，确认旧服务与旧快照仍可用。
- 物理快照生成端也单独测峰值、阻塞时长和上传体积，明确它是否增加稳态内存或恢复延迟。

## 参考

- [DuckDB 内存限制及 OOM 说明](https://duckdb.org/docs/current/guides/performance/oom)：部分分配绕过 buffer manager，因此 memory_limit 不是进程硬上限。
- [DuckDB 索引与内存](https://duckdb.org/docs/current/guides/performance/indexing)：ART 索引内存不能像普通缓冲一样驱逐；持久化索引重开后按需反序列化。
- [DuckDB 工作负载调优](https://duckdb.org/docs/current/guides/performance/how_to_tune_workloads)：线程数、插入顺序、临时磁盘、row group 大小的影响。

## 实施记录（2026-09-23）

后续按本方案实施：

- 新 v5 物理快照只保存独立 history 数据库；settings 附加库保存价格及配置。兼容已有单文件缓存的配置迁移，继续读取 v4/v3/v2 Parquet 快照。
- 生成时持有写锁，CHECKPOINT 后使用固定缓冲复制；释放锁后压缩与条件上传。恢复校验压缩哈希、数据库文件哈希、文件大小、schema/约束、引擎版本和三张表行数，再原子替换 history；并发价格更新仍保留。
- S3 当前页批量查重，返回 map 最多对应这一页；保持来源隔离、不可变 ETag 校验、晚到记录及重复回放幂等性。
- 下载并发从 16 降到 4，批次从 256 个/16MiB 降到 64 个/4MiB（单个大对象仍受 32MiB 上限约束）。

正式实现的本机隔离复测（最新生产只读快照，独立新进程）：facts 3,540,109 行、rollups 870,316 行、imported_objects 376,580 行。物理文件 684,732,416 字节；固定缓冲复制的写锁阶段约 1,099ms，复制加压缩共 9,409ms。新进程恢复（本地压缩文件→校验→解压→核对→替换附加库）约 5,864ms，峰值 RSS 54,263,808 字节，即 51.75MiB。1000 个对象查重后 Go heap 约 3MiB；包含样本键读取及 DuckDB 索引加载的峰值 RSS 约 112.67MiB。后者说明 50MiB 仅是恢复阶段目标，不是追赶/查询/后台任务的服务硬限制。

使用本地测试 PostgreSQL 与真实 uni-api 二进制的后端全量 race 回归通过。新增回归涵盖并发价格保存与连接池、损坏/截断/超限文件、取消安装、旧组合库迁移、分来源分页查重、晚到对象和 ETag 冲突。
