# DigitalOcean 历史同步反复超过两分钟

## 确认结论

根因在 uni-api-web 的历史导入器：`importS3` 串行处理来源；`importSingleS3` 又先读完来源下所有分页，再下载和提交发现的新对象。因此 DigitalOcean 的导入与下次扫描都被另一来源的完整历史扫描阻塞。`remaining_objects=0` 在分页阶段仅表示尚未汇总待处理对象，却被状态接口当作已追平。前端进一步直接建议检查 S3 导出配置，归因过早。

没有证据支持此次现象由 Fugue 故障或 DigitalOcean uni-api 导出失败造成。未修改、重启 DigitalOcean 业务服务，也未修改 Fugue 资源或路由配置。

## 修复与验证

- 各来源独立轮询，限定扫描及下载并发；一个来源的慢扫描不再阻塞其他来源下一轮。
- 每页发现的新对象立即下载、事务性导入，再继续下一页；保留完整扫描、不可变对象校验和幂等去重。
- 首次历史初始化仍等待所有来源完整扫描，原有滚动发布就绪保护保持有效。
- 来源级诊断提供扫描状态、开始/完成时间、分页数与对象数；扫描中的零待处理对象不再冒充已追平。
- 提示保留真实数据滞后告警，不直接断言导出配置异常。
- 回归测试在修复前稳定失败：第二页阻塞时，第一页已发现的事实在数据库中仍为 0；修复后在第二页阻塞期间已可查询。
- 覆盖慢来源阻塞时快来源连续完成三次扫描、状态来源隔离、取消后等待 worker 退出，以及重复扫描不重复下载/计数。
