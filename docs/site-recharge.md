# 站点实时充值（sub2api + 链动）

入口：渠道管理 → 站点账号 → 设置 → 充值设置。默认关闭。

本适配不是兑换码池：每次确认报价后才创建一笔链动订单，交给支付宝官方支付能力，核对商户付款与发货，再向绑定的 sub2api 账号提交一次兑换。只有准确兑换码出现在该账号的兑换历史中，且用户 ID、`balance` 类型、`used` 状态和正额度均匹配，才标为“已到账”。余额变化、CLI 提示和付款请求被受理都不是到账证据。

## 当前支持与边界

- 仅支持 `https://wzyp.cn/shop/<店铺编号>`、`https://pay.ldxp.cn/shop/<店铺编号>` 的单件卡密商品，以及 sub2api 的 `/api/v1/redeem` 与 `/api/v1/redeem/history`。
- 用户必须选择明确可在当前账号兑换的商品。店铺可能同时出售其他商品，不能按商品名字或价格自动认定为充值。
- 完整嵌入链接中的站点 JWT 等查询参数会被丢弃；站点凭据不发送给链动。
- 每笔先获取含手续费报价，再确认商品、站点账号和实付金额；报价有效期 5 分钟，默认上限 100 元，可设置为不超过 10000 元。下单前重新校验身份、商品、价格及设置版本。
- 首次需支付宝官方授权；后续仍可能因官方风控需要用户确认。**不承诺完全免操作，也不绕过支付宝认证、验证码或商户风控。**
- 收银台仅支持可读取的唯一支付宝官方 HTTPS 链接。仅靠 JavaScript/表单/验证码生成的收银台会停止自动付款，保留原订单供人工核对，不执行远程脚本。
- New API、云猫和其他充值协议尚未适配，不套用本流程。

## 支付运行环境（管理员前置配置）

仓库和默认镜像不会自动下载、执行或捆绑支付安装脚本，也不会继承开发者的钱包。未配置时页面明确显示“支付代理尚未配置”，禁止自动下单。

请先阅读并审查[支付宝官方支付接入文档](https://aipay.alipay.com/merchant-guide)和[官方 CLI 协议](https://github.com/alipay/payment-skills/blob/main/alipay-payment-skill/references/cashier-payment.md)，由管理员准备兼容的 `alipay-bot` 运行环境：

| 环境变量 | 含义 |
| --- | --- |
| `RECHARGE_ALIPAY_BIN` | 已审核安装的官方 CLI 绝对路径，必须可执行 |
| `RECHARGE_ALIPAY_HOME` | 当前钱包独占的持久目录，绝对路径、目录权限 0700，运行用户可读写 |
| `RECHARGE_ALIPAY_OWNER` | 唯一允许使用该钱包的控制台登录用户名，精确匹配 |
| `RECHARGE_ALIPAY_SESSION_ID` | 支付运行时提供的真实会话 ID；不得随机编造，不得借用其他人的会话 |

`HOME`/XDG 路径指向此专用目录，子进程不会继承平台、数据库或站点密钥。一个实例配置只对应一个控制台用户；不支持把一个 OS 钱包共享给多个控制台用户。多副本必须具有一致的支付运行环境、钱包身份及专用目录，或者只让专用实例执行支付；不要分别绑定成不同钱包。官方 CLI 版本/输出协议变化需重新验收；未识别状态一律视为未知。

本实现调用 `check-wallet`、`apply-wallet --agent-name uni-api-web`、`bind-wallet -c ...`、`submit-payment --session-id ... --payment-link ... --intent-summary ...`。支付提交不解析自然语言作为付款证明；由商户原订单独立确认付款。支付宝运行时和链动真实收银台的兼容性需要部署方小额人工验收，隔离模拟测试不等于真实付款验证。

## 页面配置与测试顺序

1. 打开充值设置，粘贴店铺链接，读取商品（不会下单）。
2. 仅勾选充值商品，设置订单联系方式、金额上限，明确确认可兑换到当前站点/邮箱后保存。
3. 查询钱包授权；必要时开通官方授权并提交本次授权码。不要把钱包授权码当成充值兑换码。
4. 选择已保存的充值商品，读取实时报价，确认金额后提交。关闭弹窗或刷新页面不会重发付款，原任务继续处理。
5. 从充值记录核对状态、实付金额和到账额度；需要人工处理时，可显式读取加密保存的原订单恢复资料，使用后隐藏。

本次开发只使用隔离商户、支付代理和 sub2api 模拟端点，**没有执行真实下单、付款或兑换**。上线代码不等于管理员支付环境已配置。

## 幂等、恢复与保护

- 报价、用户确认的幂等标识均唯一；同账号只允许一个未结束充值。数据库租约与钱包锁跨实例防并发。
- 在下单、付款、兑换等不支持上游幂等的写入**之前**持久化边界。崩溃/超时后只查询，不自动重发这些写入。宁可留下人工核对，也不冒重复扣款风险。
- “核对原订单并继续交付”不重新下单或付款。已保存兑换码时只读取兑换历史；尚未开始兑换且原订单确认已付款时，可继续首次兑换。
- 无订单号的未知下单、发货格式不兼容、账号变化、准确兑换记录异常进入人工核对；不会按未知状态解锁第二笔购买。当前无强制跳过/清空未知付款的按钮，需要管理员核对并处理，不能靠重试另购解决。
- 付款/卡密/查询密码/支付链接加密持久化；普通列表不返回卡密、查询密码或原始收银台。恢复接口仅同一登录用户可读，且 `Cache-Control: no-store`。日志仅包含不透明任务 ID 与标准状态。
- 有充值账目的账号受数据库外键保护，不能直接删除以免丢失恢复入口。备份时须同时保留控制数据库与原 `CONTROL_MASTER_KEY`。
- 本迁移仅新增表，不改现有检测任务、渠道路由、模型设置、站点余额或倍率。

## 本地隔离验证

运行 `npm test -- src/SiteRecharge.test.tsx src/SiteAccountSettings.test.tsx` 和 `go test ./... -run TestRecharge`。Go 的持久化用例需要 `TEST_CONTROL_DATABASE_URL` 指向专用测试 PostgreSQL，所有外部访问均重定向到 `httptest`，不访问真实店铺或钱包。覆盖完整流程、确认与报价限制、未知写入/崩溃恢复、重复/并发提交、错误账号/金额/兑换历史、跨用户隔离和凭据不出现在普通列表。
